Induction & Tree Properties

Key Definition — Perfect Binary Tree
A perfect binary tree of height h is a binary tree where (1) all leaves are on the same level and (2) every non-leaf node has exactly two children. Height 0 = a single node, which is itself the only leaf.

Theorem: A Perfect Binary Tree of Height h Has 2h Leaves

Theorem
Let P(h) be the statement "a perfect binary tree of height h has exactly 2h leaves." P(h) holds for all h ≥ 0.

Base Case — h = 0

A height-0 tree is a single node with no children. It is simultaneously the root and a leaf. Leaf count = 1 = 20. ✓

Inductive Hypothesis

Assume P(k) holds: a perfect binary tree of height k has exactly 2k leaves.

Inductive Step — Show P(k+1)

A perfect binary tree of height k+1 consists of a root with exactly two subtrees. Because the tree is perfect, each subtree is a perfect binary tree of height k. By the inductive hypothesis each has 2k leaves. The root itself is not a leaf (it has children), so all leaves of the tree come from the two subtrees:

Total leaves = 2k + 2k = 2·2k = 2k+1

P(k+1) holds. By induction, P(h) holds for all h ≥ 0. □

Corollary — Total Node Count
Summing nodes across all h+1 levels: 20+21+…+2h = 2h+1−1 (finite geometric series with r=2). So a perfect tree of height h has 2h+1−1 total nodes.
Practice: Write the general structure of an induction proof. What must the inductive step show?
Solution
An induction proof has three parts: (1) Base case — verify the claim for the smallest value (usually n=0 or n=1). (2) Inductive hypothesis — assume the claim holds for some arbitrary value k. (3) Inductive step — using only the hypothesis, prove the claim holds for k+1. The key constraint is that the inductive step must derive P(k+1) from P(k) without assuming P(k+1) itself.
Practice: How many leaves and total nodes does a perfect binary tree of height 5 have?
Solution
Leaves: 25 = 32.
Total nodes: 26−1 = 63.
Verify: level 0 has 1, level 1 has 2, …, level 5 has 32. Sum = 63.

Recurrences & Asymptotic Analysis

Master Theorem
For T(n) = aT(n/b) + f(n) (a≥1, b>1, f polynomial), compute the critical exponent crit = logb(a):
  • Case I — recursion wins: f(n) ∈ O(ncrit−ε) for some ε>0 → T(n) ∈ Θ(ncrit)
  • Case II — tie: f(n) ∈ Θ(ncrit) → T(n) ∈ Θ(ncrit log n)
  • Case III — function wins: f(n) ∈ Ω(ncrit+ε) for some ε>0 → T(n) ∈ Θ(f(n))

     = 3²(3T(n−3)+1) + 3+1  = 3³T(n−3) + 3² + 3 + 1
     ...
     = 3ⁿT(0) + 3ⁿ⁻¹ + … + 3 + 1

     = n(n−1)T(n−2) + n + 1
     = n(n−1)(n−2)T(n−3) + …
     → T(n) = n · (n−1) · (n−2) · … · 1 · T(0) + lower terms
T(n) ∈ O(n!) — factorial

T(n) = T(n/3) + T(n/4) + T(n/5) + n² (Multiple Recursive Calls)

Estimation Strategy
Since T(n/3) ≥ T(n/4) ≥ T(n/5), bound above by 3T(n/3)+n². Apply Master Theorem: crit = nlog₃3 = n. Since n² ∈ Ω(n1+ε), Case III applies → T(n) = Θ(n²).
Practice: Solve T(n) = 2T(n/4) + n using the Master Theorem.
Solution

Since n ∈ Ω(n0.5+ε) for ε=0.5, we are in Case III.
Answer: T(n) = Θ(n).
Practice: Why can't the Master Theorem be applied to T(n) = T(n−1) + n?
Solution
The Master Theorem requires the form T(n) = aT(n/b) + f(n) where b>1. T(n−1) subtracts a constant, not divides by a constant — the problem size shrinks by subtraction, not by a fixed ratio. Unrolling: T(n) = T(n−1)+n = T(n−2)+(n−1)+n = … = T(0)+1+2+…+n = n(n+1)/2 ∈ Θ(n²).

Insertion Sort — Deep Dive

Core idea: Maintain a sorted prefix of the list. For each new element at position i, "insert" it into its correct position in the already-sorted prefix by swapping leftward until the invariant is restored.

Pseudocode

InsertionSort(A):
  for i = 1 to n−1:            // outer loop: grows sorted prefix
    j = i
    while j > 0 and A[j] < A[j−1]:
      swap(A[j], A[j−1])           // bubble element left
      j−−
  return A

Loop Invariant

Invariant
At the start of each outer-loop iteration i, the subarray A[0..i−1] is sorted. After the last iteration (i = n−1), A[0..n−1] is sorted.

Step-by-Step Trace — A = [5, 3, 4, 1, 2]

Initial: [5, 3, 4, 1, 2]
i=1: j=1, 3<5 → swap → [3, 5, 4, 1, 2]   j=0, stop
i=2: j=2, 4<5 → swap → [3, 4, 5, 1, 2]   4>3, stop → [3, 4, 5, 1, 2]
i=3: j=3, 1<5 → swap → [3,4,1,5,2] → 1<4 → [3,1,4,5,2] → 1<3 → [1,3,4,5,2]
i=4: j=4, 2<5,4,3 → [1,2,3,4,5] ✓

Runtime Analysis

Best Case — Θ(n)
Input already sorted. The while condition A[j]<A[j−1] fails immediately every time. Outer loop runs n−1 times with O(1) work each → Θ(n).
Average Case — Θ(n²)
On average, each element travels halfway back. Total swaps ≈ n(n−1)/4 ∈ Θ(n²).
Worst Case — Θ(n²)
Reverse-sorted input. Element at position i must swap all the way to position 0 (i swaps). Total: 1+2+…+(n−1) = n(n−1)/2 ∈ Θ(n²).

Inductive Proof of O(n²) Worst Case

Claim
The worst-case number of swaps made by Insertion Sort on a list of size n is at most n(n−1)/2.

Base case n=1: 0 swaps needed. Formula: 1·0/2 = 0. ✓

Hypothesis: Assume a list of size n requires at most n(n−1)/2 swaps in the worst case.

Step (n → n+1): When element at position n is inserted, j decrements from n down toward 0. It can swap at most n times (positions n,n−1,…,1 — it cannot swap to position −1 since j>0 must hold). Therefore:

Total swaps ≤ n(n−1)/2 + n = [n(n−1) + 2n] / 2 = n(n+1)/2 = (n+1)((n+1)−1)/2 ✓

Since swaps ≤ n(n−1)/2 ∈ O(n²), insertion sort is O(n²) in the worst case. □

Practice (Fa21 Q1): What is the worst-case input for Insertion Sort, and how many swaps does it trigger?
Solution
The worst case is a reverse-sorted list, e.g. [n, n−1, …, 2, 1]. Element at position i is larger than all previous elements in the sorted prefix, so it must bubble all the way to position 0, making i swaps. Total swaps = 1+2+…+(n−1) = n(n−1)/2.

Merge Sort — Deep Dive

Core idea: Divide-and-conquer. Recursively split the array in half until each piece has size 1 (trivially sorted), then merge sorted halves back together in linear time.

Pseudocode

MergeSort(A, lo, hi):
  if lo >= hi: return                     // base case: one element
  mid = (lo + hi) / 2
  MergeSort(A, lo, mid)
  MergeSort(A, mid+1, hi)
  Merge(A, lo, mid, hi)              // merge two sorted halves

Merge(A, lo, mid, hi):
  L = A[lo..mid],  R = A[mid+1..hi]   // copy to temp arrays
  i = j = 0;  k = lo
  while i < L.len and j < R.len:
    if L[i] <= R[j]: A[k++] = L[i++]
    else:            A[k++] = R[j++]
  // copy remaining elements
  while i < L.len: A[k++] = L[i++]
  while j < R.len: A[k++] = R[j++]

Recurrence and Solution

T(n) = 2T(n/2) + Θ(n)

Here a=2, b=2, f(n)=n. crit = nlog₂2 = n1. Since f(n)=n=Θ(n1), this is Case II of the Master Theorem → T(n) = Θ(n log n).

Recursion Tree Intuition

Why Θ(n log n)?
The recursion tree has log₂n levels (each level halves the problem). At each level, the total work across all merge calls is exactly Θ(n) (every element is touched once per level). Multiplying: log n levels × n work per level = Θ(n log n).

Why All Cases Are Identical

No "Lucky" Path Through Merge Sort
Unlike QuickSort, Merge Sort always splits exactly in half regardless of input values — the midpoint is computed from indices, not element values. The merge step always scans all n elements. There is no shortcut even for already-sorted input. Every run of MergeSort on n elements takes exactly Θ(n log n): best = worst = average.

Step-by-Step Trace — A = [5, 3, 1, 4, 2]

Split: [5,3,1,4,2] → [5,3,1] | [4,2]
Split: [5,3,1] → [5,3] | [1] and [4,2] → [4] | [2]
Split: [5,3] → [5] | [3]
Merge: [5]+[3] → [3,5]
Merge: [3,5]+[1] → [1,3,5]
Merge: [4]+[2] → [2,4]
Merge: [1,3,5]+[2,4] → [1,2,3,4,5] ✓
Practice: What is the space complexity of Merge Sort, and why?
Solution
O(n) auxiliary space. The Merge step copies both halves into temporary arrays before writing back. At any given level, the total copied data is O(n). The recursive call stack adds O(log n) frames but this is dominated by the O(n) merge buffers. (Some implementations reduce this with in-place merging, but those are more complex.)

QuickSort — Deep Dive

Core idea: Choose a pivot element. Partition the array so all elements less than the pivot come before it and all elements greater come after. Then recursively sort each side.

Pseudocode (Middle-Element Pivot)

QuickSort(A, lo, hi):
  if lo >= hi: return
  pivot_idx = Partition(A, lo, hi)
  QuickSort(A, lo, pivot_idx − 1)
  QuickSort(A, pivot_idx + 1, hi)

Partition(A, lo, hi):
  pivot = A[(lo+hi)/2]              // middle-element pivot
  // swap pivot to end, then two-pointer partition
  i = lo − 1
  for j = lo to hi−1:
    if A[j] <= pivot:
      i++; swap(A[i], A[j])
  swap(A[i+1], A[hi])
  return i + 1

Best Case — Θ(n log n)

Balanced Partition Every Time
The pivot always splits the array into two halves of roughly equal size. The recurrence becomes T(n) = 2T(n/2) + Θ(n), identical to Merge Sort → Θ(n log n). This happens when the pivot is always near the median.

Worst Case — Θ(n²)

Worst Case with Middle-Element Pivot
Consider the already-sorted or reverse-sorted array. With a middle-element pivot, the element at the middle index is the median of a sorted array — so it's actually a good split! But consider the input [1, 3, 2, 4] or carefully constructed adversarial inputs where the middle element is always the min or max of the remaining subarray. Each partition produces a 0/(n−1) or 1/(n−2) split, giving recurrence:
T(n) = T(n−1) + T(0) + Θ(n) = T(n−1) + Θ(n)
Unrolling: Θ(n) + Θ(n−1) + … + Θ(1) = Θ(n²).
Exam-Specific Worst Case
The Spring 2025 exam specifically asks about middle-element pivot. A concrete worst case: any array where the median of each subarray happens to be at one end — e.g. an array like [1, 2, 3, …, n] when sorted in a pattern that puts extremes in the middle on each recursive call. In general, the worst case is when every partition is maximally unbalanced.

Step-by-Step Trace (Best Case, Balanced)

A=[3,1,4,5,2], pivot=A[2]=4
Partition: [3,1,2] | 4 | [5] → pivot at idx 3
Recurse left: [3,1,2], pivot=A[1]=1 → [] | 1 | [3,2]
Recurse right of 1: [3,2], pivot=A[0]=3 → [2] | 3 | []
Result: [1,2,3,4,5] ✓

QuickSort vs Merge Sort

QuickSort Advantages
O(log n) space (in-place partitioning). Excellent cache locality. Faster in practice for random data due to small constants.
Merge Sort Advantages
Guaranteed Θ(n log n) worst case. Stable sort. Better for linked lists and external sorting. Predictable performance.
Practice: What is the recurrence for QuickSort's worst case, and how do you solve it?
Solution
Worst case: one partition is size 0, the other is n−1. Recurrence: T(n) = T(n−1) + T(0) + Θ(n) = T(n−1) + Θ(n) since T(0)=O(1).
Unrolling: T(n) = Θ(n) + Θ(n−1) + … + Θ(1) = Θ(n(n+1)/2) = Θ(n²).

Comparison Sort Lower Bound

Theorem
Any comparison-based sorting algorithm must make at least Ω(n log n) comparisons in the worst case.

The proof uses decision trees — a model that captures all possible comparison sequences any sorting algorithm can make.

The 5-Step Argument

  • 1
    n! permutations exist. For a list of n distinct elements, there are n choices for the first position, n−1 for the second, …, giving n! total orderings. Any possible initial order of the input corresponds to exactly one permutation.
  • 2
    Every permutation must be producible. For any input ordering, there exists exactly one permutation that sorts it. If the algorithm's decision tree is missing a leaf for some permutation, then that input ordering cannot be correctly sorted → the algorithm is incorrect.
  • 3
    A decision tree for n elements has at least n! leaves. Each leaf corresponds to one output permutation (one way to re-order the elements). We need at least one leaf per permutation, so the tree has ≥ n! leaves.
  • 4
    A binary tree with ≥ n! leaves has height ≥ log₂(n!). A binary tree of height h has at most 2h leaves. So 2h ≥ n! → h ≥ log₂(n!). By Stirling's Approximation n! ≈ √(2πn)(n/e)n: log₂(n!) ≈ ½·log₂(2πn) + n·log₂(n) − n·log₂(e) = Θ(n log n)
  • 5
    Height = worst-case comparisons. The height of the decision tree is the length of the longest root-to-leaf path, which equals the maximum number of comparisons in the worst case. Since height ≥ Θ(n log n), any comparison sort takes Ω(n log n) comparisons in the worst case.
Does the tree height have to be exactly n log n?
No. The height must be at least n log n — it can be more (an inefficient sort), but it cannot be less. If it were, there wouldn't be enough leaves for all n! permutations, and some input couldn't be sorted. Merge Sort and heap sort achieve the optimal Θ(n log n). Insertion sort is suboptimal in the worst case.
Practice (Fa21 Q2e): Does the decision tree height have to be n log n? Why or why not?
Solution
It does NOT have to be exactly n log n. The lower bound proves the height cannot be less than Θ(n log n). It can be greater (e.g., Bubble Sort, which has a taller decision tree because it makes redundant comparisons). The bound is tight in the sense that sorting algorithms like Merge Sort achieve exactly Θ(n log n) height.

Radix Sort (LSD) — Deep Dive

Core idea: Sort digit-by-digit starting from the least significant digit (rightmost) to the most significant digit (leftmost). Each digit-pass uses a stable counting sort.

What is a Stable Sort?

Stability Defined
A sort is stable if elements with equal keys maintain their original relative order. Example: sorting [(10,A),(11,A),(10,B),(11,B)] by the number stably gives [(10,A),(10,B),(11,A),(11,B)] — A still comes before B for ties.

Why Radix Sort Must Use a Stable Sub-Sort

After sorting by the 1s digit, numbers with the same ones digit are ordered correctly relative to each other. When we sort by the 10s digit next, numbers with the same tens digit must preserve their prior ones-digit order. An unstable sort at this step would re-scramble elements that have equal tens digits, destroying the work done in the previous pass.

Example of Instability Breaking Radix Sort
After pass 1 (1s digit): [31, 51, 22, 32, 23, 53, 34, 54]
Stable sort by 10s: → [22, 23, 31, 32, 34, 51, 53, 54] ✓
Unstable sort by 10s (scrambles 3X): → [23, 22, 32, 34, 31, 53, 54, 51] ✗ (31, 51 out of order)

Complexity Analysis

Time — O(d·n)
d digit passes × O(n) counting sort per pass. For fixed-width integers (d=constant) this is Θ(n).
Space — O(n+k)
O(k) for the counting array (k = base, e.g. 10 for decimal) + O(n) output buffer. k is a constant so O(n) overall.
Why O(n) Radix Sort Doesn't Violate the Ω(n log n) Lower Bound
The comparison sort lower bound applies only to algorithms that sort by pairwise comparisons of elements (x<y?). Radix sort never compares two elements against each other — it inspects individual digits and uses counting sort. It exploits the structure of the keys. The decision-tree argument doesn't apply to non-comparison sorts, so there is no contradiction.
Practice: Why does LSD Radix Sort process digits from right to left rather than left to right?
Solution
If we processed most-significant digit first (MSD), we'd correctly group by the leading digit but would need to independently sort each group recursively — this requires extra bookkeeping and partitioning logic. LSD processes least-significant first: each pass establishes a partial order that is preserved (via stability) by subsequent passes. By the time we sort the most-significant digit last, all lower-priority orderings are already correctly embedded in the sequence.

Dynamic Programming — LCS

The Longest Common Subsequence (LCS) finds the longest sequence of characters present in both strings (in order, but not necessarily contiguous). Example: LCS("abacde", "abcefa") = "abce".

Recursive Algorithm (No Memoization)

lcs(A, B, i=0, j=0):
  if i >= A.len or j >= B.len: return 0   // base case
  no_A = lcs(A, B, i+1, j)            // skip A[i]
  no_B = lcs(A, B, i, j+1)            // skip B[j]
  if A[i] == B[j]:
    match = 1 + lcs(A, B, i+1, j+1)   // match both
  else:
    match = lcs(A, B, i+1, j+1)       // advance both (no match)
  return max(match, no_A, no_B)

Runtime Without Memoization — O(3m+n)

Each call spawns 3 recursive calls. The maximum depth is m+n (both pointers reach the end). At depth d there are up to 3d calls. Total calls ≤ 3m+n, giving O(3m+n) — exponential.

Why Memoization Works

Overlapping Subproblems
The strings A and B never change between calls — only the indices (i, j) change. Two calls with the same (i, j) will always return the same value. There are only (m+1)×(n+1) distinct (i,j) pairs. Without memoization, exponentially many redundant calls are made to the same states.

What values can i and j hold?

i ∈ {0, 1, 2, …, |A|} and j ∈ {0, 1, 2, …, |B|}. They can equal the string length (this triggers the base case returning 0). So i has |A|+1 possible values and j has |B|+1 possible values.

Memoized Version

// Initialize memo table to −1 (uncomputed)
memo = [−1] × (m+1) × (n+1)

lcs_memo(A, B, i, j):
  if i >= A.len or j >= B.len: return 0
  if memo[i][j] != −1: return memo[i][j]   // cached!
  no_A = lcs_memo(A, B, i+1, j)
  no_B = lcs_memo(A, B, i, j+1)
  if A[i] == B[j]: match = 1 + lcs_memo(A, B, i+1, j+1)
  else: match = lcs_memo(A, B, i+1, j+1)
  memo[i][j] = max(match, no_A, no_B)
  return memo[i][j]
Table Size
(m+1) × (n+1) entries, one per (i,j) pair.
Runtime with Memoization
Each cell filled once in O(1) → Θ(mn) total.
Practice: For LCS of strings of length 6 and 8, what is the table size and runtime?
Solution
i ∈ {0,…,6} = 7 values. j ∈ {0,…,8} = 9 values.
Table size: 7 × 9 = 63 entries.
Runtime: Θ(6×8) = Θ(48) = Θ(mn).
Practice: Why don't we memoize on A and B (the strings themselves)?
Solution
A and B are constant across all recursive calls — they are never modified. Memoization caches results keyed on the inputs that vary. Since only (i, j) vary between calls, we only need to memoize on (i, j). Including A and B in the key would be redundant (they're always the same) and would prevent cache hits.

Breadth-First Search (BFS)

Explores all neighbors at distance d before moving to distance d+1. Uses a FIFO queue. Tracks visited set to avoid cycles.

BFS(G, start):
  visited = {start};  queue = [start]
  order = []
  while queue not empty:
    node = queue.dequeue()
    order.append(node)
    for neighbor in sorted(G.adj[node]):     // alphabetical
      if neighbor not in visited:
        visited.add(neighbor)
        queue.enqueue(neighbor)
  return order

Dequeue order: a, b, c, d, e, f, g, h, i
BFS Properties
Time: O(V+E). Space: O(V). Finds shortest paths (in terms of number of edges) from the source. Level k nodes are all at distance k from source.

Depth-First Search (DFS)

Explores as deep as possible before backtracking. Uses a LIFO stack. Note: with explicit stack, neighbors are pushed in reverse order so the alphabetically-first is popped first.

DFS(G, start):
  visited = {};  stack = [start]
  order = []
  while stack not empty:
    node = stack.pop()
    if node in visited: continue
    visited.add(node);  order.append(node)
    for neighbor in reverse_sorted(G.adj[node]):  // reverse alpha
      if neighbor not in visited:
        stack.push(neighbor)
  return order

Traced DFS Example — Same graph, starting at a (reverse alphabetical adj lists)

Stack: [a]   Pop a → push d,c,b (rev-alpha order so b popped first)
Stack: [d,c,b]   Pop b → push f,e
Stack: [d,c,f,e]   Pop e → no unvisited neighbors
Stack: [d,c,f]   Pop f → no unvisited neighbors
Stack: [d,c]   Pop c → push g
Stack: [d,g]   Pop g → no unvisited neighbors
Stack: [d]   Pop d → push i,h
Stack: [i,h]   Pop h, then pop i
Pop order: a, b, e, f, c, g, d, h, i
Exam Tip — Ordering
BFS adjacency lists: alphabetical. DFS adjacency lists: reverse alphabetical when using an explicit stack (so the first-alphabetical neighbor is pushed last and popped first). Always read the exam instructions carefully.

Modified BFS — k-Friends Problem (Fa21 Q5)

Find all nodes that are within degree ≤ k of both v1 and v2 (common "k-friends").

  • 1Run BFS from v1; record dist1[v] = distance from v1 to every vertex v.
  • 2Run BFS from v2; record dist2[v] = distance from v2 to every vertex v.
  • 3Scan all vertices: report v if dist1[v] ≤ k and dist2[v] ≤ k.

Complexity: Two BFS passes = 2·O(V+E), plus O(V) scan = O(V+E).

Dijkstra's Algorithm

Finds shortest paths from a single source in graphs with non-negative edge weights.

Dijkstra(G, src):
  dist[src]=0;  dist[v]=∞ for all v≠src
  pred[v]=null for all v
  Q = min-priority queue of all vertices keyed by dist
  while Q not empty:
    u = Q.extract_min()
    for each neighbor v of u:
      alt = dist[u] + weight(u,v)
      if alt < dist[v]:
        dist[v] = alt;  pred[v] = u
        Q.decrease_key(v, alt)

Why Dijkstra Fails on Negative Edges
Once a node u is extracted from the min-heap, Dijkstra declares dist[u] final. But a negative edge encountered later could give a shorter path to u through some not-yet-extracted node v. The greedy "finalize on extraction" assumption breaks down — negative edges allow "going backward" to improve already-finalized distances.

Bellman-Ford Algorithm

Relaxes all edges |V|−1 times. Handles negative-weight edges. Detects negative-weight cycles.

BellmanFord(G, src):
  dist[src]=0;  dist[v]=∞ for all v≠src
  for iter = 1 to |V|−1:
    for each edge (u,v,w) in G.edges:
      if dist[u]+w < dist[v]:
        dist[v] = dist[u]+w;  pred[v] = u
  // Negative cycle detection
  for each edge (u,v,w):
    if dist[u]+w < dist[v]: report negative cycle
Negative Cycle Problem (Sp25 Q10)
Graph: a→b (5), b→c (−20), c→d (8), d→c (−4→ wait: exam has c→a=5, d→c=−4), c→a (5). Edge sequence given: a→b, c→d, c→a, d→c, b→c.

The cycle b→c→a→b has total weight −20+5+5 = −10. Each time around the cycle, all reachable distances decrease. Bellman-Ford keeps relaxing indefinitely, producing −∞ values. Detection: if any edge still relaxes after |V|−1 = 4 iterations, a negative cycle exists.
Init: dist = {a:0, b:∞, c:∞, d:∞}
Iter 1: a→b → dist[b]=5; b→c → dist[c]=−15; c→a → dist[a]=−10; d→c: no update; c→d → dist[d]=−7
Iter 2: a→b → dist[b]=−5; b→c → dist[c]=−25; c→a → dist[a]=−20 … values keep shrinking
After |V|−1 iters: still relaxable → NEGATIVE CYCLE DETECTED
Bellman-Ford: O(VE)
|V|−1 iterations × |E| edges per iteration. Slower than Dijkstra but handles negative edges.
Dijkstra: O((V+E) log V)
With binary heap. Only valid for non-negative weights. Much faster in practice.

Kruskal's Algorithm — Minimum Spanning Tree

Greedily adds the cheapest edge that doesn't create a cycle, until |V|−1 edges are selected.

Kruskal(G):
  sort edges by weight (ascending)
  forest = UnionFind(V)    // each vertex in its own set
  MST = []
  for each edge (u,v,w) in sorted order:
    if forest.find(u) != forest.find(v):  // different components
      MST.append((u,v,w))
      forest.union(u, v)
      if MST.size == |V|−1: break
  return MST

Practice: Why does Kruskal's produce a minimum spanning tree (not just a spanning tree)?
Solution
By the "cut property": for any cut of the graph (partition of vertices into two sets), the minimum-weight edge crossing the cut is always in some MST. Kruskal's greedily picks the global minimum available edge that doesn't create a cycle. At each step, this edge is the minimum crossing some cut of the current forest — so by the cut property, it belongs in the MST. Proof by induction shows the greedy choice is always safe.

NP-Completeness & Problem Complexity

P
Problems solvable in polynomial time. Examples: sorting, Dijkstra's, MST, LCS.
NP
Problems whose proposed solutions can be verified in polynomial time. P ⊆ NP. Unknown if P = NP.
NP-Complete
In NP AND every NP problem reduces to it in poly-time. "Hardest" problems in NP. SAT is the canonical example.

SAT (Satisfiability)

Given φ(x₁,…,xₙ) — a boolean formula using ∧, ∨, ¬ — does there exist a truth assignment making φ = True?

Example: φ = ¬x₁ ∧ (x₂ ∨ x₃). Assignment (False, True, False) makes φ = True.

SAT ∈ NP — Verification Algorithm
Certificate: A boolean assignment (T/F for each of the n variables).
Verifier: Substitute all variable values into φ. Evaluate using the formula's structure — in the worst case (deeply nested formula) this takes O(n²). Since O(n²) is polynomial, the verifier runs in polynomial time → SAT ∈ NP. □
Why NP-Complete ≠ Not in P
SAT is NP-Complete means: (1) SAT ∈ NP and (2) every NP problem reduces to SAT in poly-time. This does NOT prove SAT ∉ P. If someone found a poly-time algorithm for SAT, it would prove P = NP (and solve all NP problems). We simply don't know yet whether such an algorithm exists. The open question P vs. NP remains the most famous unsolved problem in computer science.

TSP(k) — Traveling Salesman Restriction

TSP asks for the minimum-cost Hamiltonian cycle (visits every vertex exactly once and returns). TSP(k): does a Hamiltonian cycle of cost exactly k exist?

TSP(k) ∈ NP — Verification Algorithm
What a solution looks like: An ordered permutation of all |V| vertices — a proposed Hamiltonian cycle.
verify_TSP_k(G=(V,E,w), path, k):
  if |path| != |V|: return False           // wrong length
  if path has any repeated vertex: return False
  total = 0
  for i = 0 to |V|−1:
    u = path[i];  v = path[(i+1) % |V|]    // wrap-around last edge
    if (u,v) ∉ E: return False
    total += w(u, v)
  return total == k                         // cost exactly k?
This runs in O(|V|) — polynomial. Therefore TSP(k) ∈ NP. □
Practice: What distinguishes NP-Complete from NP-Hard?
Solution
NP-Complete = in NP AND NP-Hard. NP-Hard = every NP problem reduces to it in poly-time, but it may NOT itself be in NP (i.e., solutions may not be verifiable in poly-time). Example: the Halting Problem is NP-Hard but not in NP (and not NP-Complete) since we can't even verify "this program halts" in polynomial time.
Practice (Fa21 Q10): Show that SAT ∈ NP by describing the certificate and verifier.
Solution
Certificate: a truth assignment — a list of n Boolean values, one per variable.
Verifier: Substitute the assignment into φ. Traverse the formula tree: evaluate each atomic clause (e.g., ¬x₁ = not False = True), then combine using ∧ and ∨ operators bottom-up. The formula has at most O(n) operators and O(n) clauses, so evaluation takes O(n²) at worst (each operator may trigger a sub-traversal). O(n²) is polynomial → SAT ∈ NP. □

Algorithm Design — Min-Range Subarray

Problem (Sp25 Q6): Given array A = [a₁,…,aₙ], create array B of exactly k elements from A such that max(B)−min(B) is minimized.

Key Insight

Why Consecutive Elements in Sorted Order Are Optimal
If B contains any two elements that are not adjacent in sorted A, we can always reduce max(B)−min(B) by replacing the outlier with the element adjacent to the closest remaining element. Therefore the optimal B is always a window of k consecutive elements in the sorted array.

Example Trace — A = [1, 2, 7, 12, 15, 16], k = 3

Sorted A: [1, 2, 7, 12, 15, 16]
Window [1,2,7]: max−min = 7−1 = 6
Window [2,7,12]: max−min = 12−2 = 10
Window [7,12,15]: max−min = 15−7 = 8
Window [12,15,16]: max−min = 16−12 = 4 ← minimum
→ B = [12, 15, 16], range = 4

Pseudocode

min_range_subarray(A, k):
  sorted_A = sort(A)                  // O(n log n)
  best_range = ∞
  best_start = 0
  for i = 0 to n−k:                   // O(n) sliding window
    range = sorted_A[i+k−1] − sorted_A[i]
    if range < best_range:
      best_range = range
      best_start = i
  return sorted_A[best_start .. best_start+k−1]
Time Complexity — O(n log n)
Sort: O(n log n). Sliding window: O(n−k+1) = O(n). Total dominated by sort: O(n log n).
Space Complexity — O(n)
O(n) for sorted copy. O(1) extra for the window scan. Sorting stack: O(log n).

Edge Cases to Consider

  • k = 1: Any single element. Range = 0. Return any element.
  • k = n: Must take all elements. Return entire sorted array.
  • Ties: Multiple windows may achieve the same minimum range; return any.
  • Unsorted input: Algorithm handles this — sorting is the first step.
